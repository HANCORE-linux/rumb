# AGENTS.md

Rules for AI agents working on rumb. The maintainer decides; when in doubt, ask.

## Approval

- Ask the maintainer before every step that records or publishes work: commit, push, pull request, merge, tag and GitHub release. One approval covers only the steps it names.
- Never force-push, and never push `main` directly.
- Design changes need approval before any code is written (see [Design](#design)).

## Releases

Every release takes the same path, and each step waits for the maintainer's approval:

1. Create a worktree with a release branch from `main`:
   `git worktree add ../rumb-X.Y.Z -b release-X.Y.Z main`
2. Do the work there. The release commit sets the version in `tui/Cargo.toml` and in the `rumb` entry of `tui/Cargo.lock`, the date in `man/rumb.1`, and refreshes `docs/overview.png` from the demo data at the same moment as before (frame 480 of the `motion_frames` test: 170×50, Labra).
3. Push the branch.
4. Open a pull request against `main`.
5. Merge it once the maintainer approves and CI is green.
6. Tag the merge commit `vX.Y.Z` (a lightweight tag, like the earlier ones). CI fails when the tag does not match the crate version.
7. Create the GitHub release. The title is the bare version (`vX.Y.Z`). The notes start with `## What's Changed`, group the changes under `### Features` and `### Bug Fixes` as bullets beginning with `**feat:**` or `**fix:**` and ending with the short commit hash, and close with `**Full Changelog**: https://github.com/HANCORE-linux/rumb/compare/vPREVIOUS...vX.Y.Z`. Add `### Documentation` with `**docs:**` bullets only when the release changes the documentation. Each bullet says what works now, phrased positively; there is no verification section.

The Omarchy package lives in [omacom/omarchy-pkgs](https://github.com/omacom/omarchy-pkgs). The maintainer's account is vouched there, so a green package PR merges and publishes itself. Open or update one only on the maintainer's go.

## Hard rules

- rumb only reads. It never runs or names sudo, pkexec, doas, su or run0, and `checkupdates` never gets `-d`. `tui/tests/no_privilege_escalation.rs` enforces this for `bin/`, `tui/src/` and `tui/export-themes`.
- Commits use the account's GitHub noreply address. Check `git log --format='%ae %ce'` before every push.
- Never commit personal data: no real email addresses, and no screenshots or recordings of a real system. The pictures in `docs/` come from the demo data.
- No AI attribution in commits or pull requests: no Co-Authored-By lines for agents, no "Generated with" footers.
- Commit messages have a short imperative subject in English, like the existing history.
- Plain Arch Linux keeps working. Omarchy, Hyprland, nvidia, snapper and yay/paru are optional; check that a tool exists before using it.
- Do not edit Omarchy theme files or switch the system theme. `tui/themes.json` is generated by `tui/export-themes`.

## Checks

Run what CI runs before asking to commit:

```sh
cd tui
cargo clippy --locked --release --all-targets -- -D warnings
cargo test --locked --release
cd .. && shellcheck --severity=warning bin/rumb-scan tui/export-themes
```

Verify a change on the real binary as well: `rumb --demo`, or a recorded stream played through a fake scanner (`RUMB_SCAN` points rumb at any script that prints the stream). Say what you did not check.

## Design

The look of rumb is the maintainer's. **Design changes are not allowed, only proposals.** This covers the layout, colours, text on screen, the pictures, the eye and its motion.

- Propose a design change as before/after pictures rendered from the real program. Mockups live in a scratch copy, never in product code. Keep them out of the repository (`visualizations/` is ignored by git).
- Only a proposal the maintainer has approved goes into the code, exactly as approved.
- The maintainer judges how it looks; passing tests are not that verdict.
- Every text on screen is data, a legend or a key hint. No filler.
- A value that is not known yet stays empty. No guessed or placeholder values.
- Each fact appears once per screen. A detail window adds information instead of repeating what is visible.
- Colour is a signal only: red means act, yellow means look, the theme accent (pink in Labra) means problem, green means "belongs to the selected update". Everything else is neutral ink.
- Text stays readable: at least 4.5:1 contrast in every bundled palette (tested in `tui/src/theme.rs`).
- UI text is English and every term is accurate: units, plurals, full numbers as `1,915`, dates as `MM-DD HH:MM`.
- Colours come from the current Omarchy theme, with Labra as the fallback.
- The eye stays calm: it glances at a selection and looks back; it does not stare.

## Code

- Match the surrounding code: naming, density and idiom. Do not add explanatory comments; keep the existing doc comments.
- The scanner and the dashboard talk through the event stream. Read new stream fields with `#[serde(default)]` so older streams still load, and show them in `tui/demo.ndjson`.
- Keep heavy work such as painting and encoding pictures off the UI thread, and measure CPU when the eye or an animation changes.

## Tools

| Variable | Use |
|---|---|
| `RUMB_SCAN` | path of the scanner to run, for example a fake one for tests |
| `RUMB_THEME` | theme name, like `--theme` |
| `RUMB_EVENTS` | a recorded stream for the frame tests instead of the demo |
| `RUMB_DUMP` | output directory for the `mockup_frames` test: cell grid as JSON plus pictures |
| `RUMB_VIDEO` | output directory for the `motion_frames` test, with `RUMB_ONLY`, `RUMB_SECONDS`, `RUMB_COLUMNS`, `RUMB_ROWS`, `RUMB_CELL_WIDTH`, `RUMB_CELL_HEIGHT` and `RUMB_SELECT` |
